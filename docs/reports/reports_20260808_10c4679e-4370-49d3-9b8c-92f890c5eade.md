## 2. 障害 #1: Silver フルスコープ実行が無出力のまま終了

| 項目 | 内容 |
|------|------|
| 重大度 | HIGH |
| コマンド | `uv run python src/main.py ingest-jepx-bronze-to-silver` (年度指定なし) |
| 発生時刻 | 2026-08-08 04:52:26 開始 |
| 症状 | 5 分超で応答なし → バックグラウンド移行。ログは `No schema changes detected` (1 テーブル目のスキーマ確認) で途切れ、**upsert 結果行が一切出力されないまま終了** |

### 影響

`silver.jepx_spot_price_base` の行数は実行前後で 5,856 行のまま変化せず、22 年度分 374,400 行の書き込みが 1 件も反映されなかった。

### 検出時の注意点

ハーネスのタスク通知は `completed (exit code 0)` を報告したが、実際にはデータが 1 行も書かれていなかった。
**通知のステータスのみを完了判定に使うと、この障害は見逃される。**
本実行では書き込み後に行数を実測したことで検出できた。

### 原因

障害 #2 と同一 (PyIceberg `upsert()` のマッチ述語構築コスト)。
374,400 行 × 3 テーブルを単一トランザクションで upsert しようとして、実用時間内に完了しなかった。

## 3. 障害 #2: Silver area テーブルの upsert が SIGSEGV でクラッシュ

| 項目 | 内容 |
|------|------|
| 重大度 | **CRITICAL** |
| コマンド | `uv run python src/main.py ingest-jepx-bronze-to-silver --fiscal-year 2026` |
| execution_id | `10c4679e-4370-49d3-9b8c-92f890c5eade` |
| 発生時刻 | 05:16:20 開始 → 05:27:43 異常終了 (11 分 22 秒) |
| 終了コード | **139 (SIGSEGV = 128 + 11)** |

### 経過

| 時刻 | テーブル | 結果 | 所要 |
|------|---------|------|------|
| 05:17:54 | `silver.jepx_spot_price_base` | 成功 (updated=5,856 / inserted=432) | 1分31秒 |
| 05:19:40 | `silver.jepx_spot_price_block` | 成功 (updated=5,856 / inserted=432) | 1分46秒 |
| 05:19:40〜 | `silver.jepx_spot_price_area` | **クラッシュ (コミットなし)** | 約8分後に SIGSEGV |

### 影響

- `base` / `block` は FY2026 が正常反映
- `area` のみ FY2026 が旧スナップショット (52,704 行) のまま取り残され、**3,888 行が欠損**
- Iceberg のコミットはアトミックなため、テーブル自体の破損はなし (未コミットで終了)

### 原因

PyIceberg の `Transaction.upsert()` は、書き込み前に `upsert_util.create_match_filter(df, join_cols)`
で**ソースフレームの全ジョインキーを OR 連結した巨大な述語**を構築し、それを対象テーブルへスキャンする。

`silver.jepx_spot_price_area` の場合:

- ジョインキー: `(delivery_date, time_code, area_name)` の 3 列
- ソース行数: 56,592 行 → 述語項数 56,592
- 対象テーブル: 3,361,008 行

この規模で述語構築とスキャンを行うとメモリが破綻し、セグメンテーション違反に至った。
コンテナの搭載メモリは 15 GB (実行時の空き 約 9 GB) で、OS レベルのメモリ不足ではなくプロセス内での破綻。

### 通知ステータスと実際の終了コードの乖離 (要注意)

ハーネスのタスク通知は `completed (exit code 0)` を報告した。
これは**ラッパーシェルの終了コード**であり、Python プロセスの実際の終了コードではない。
実際の `139` は、コマンド内で `echo "exit=$?"` により明示的に捕捉して初めて判明した。

> **教訓**: バックグラウンド実行の成否は、通知ステータスではなく
> (a) プロセスの終了コードを明示的に捕捉する、(b) 書き込み後の行数を実測する、
> のいずれかで判定すること。

## 4. 調査項目: area テーブルの 2011年 / 2018年 の行数差異 (障害ではない)

検証中に `area` の行数が `base × 9` と一致しない年度を検出したため調査した。
**結論: ソースデータ由来の正常な挙動であり、パイプラインの不具合ではない。**

| 年 | 期待 (base×9) | 実際 | 差分 | 原因 |
|----|---------------|------|------|------|
| 2011 | 157,680 | 153,936 | -3,744 | `area_price_tokyo` がソースで NULL (震災後の計画停電期間) |
| 2018 | 157,680 | 156,720 | -960 | `area_price_hokkaido` がソースで NULL (北海道胆振東部地震のブラックアウト期間) |

Bronze 側の NULL 件数を集計したところ、上記の欠損数と完全に一致した。
`extract_area_frame()` が使う DuckDB の `UNPIVOT` は既定で NULL 値を除外するため、
該当セルは area 行として出力されない。エリア別行数でも `tokyo` と `hokkaido` のみが少なく、実データと整合する。

> 再調査を防ぐため記録: この 2 年度の差異は**期待される挙動**。

## 5. 回避策と性能比較

書き込み方式を対象データの性質に合わせて切り替えることで解消した。

| 方式 | 適用範囲 | 所要時間 |
|------|---------|---------|
| `table.upsert()` | FY2005 (単年度) | 3分21秒 |
| `table.upsert()` | FY2006 (単年度) | 4分31秒 (テーブル肥大により増加) |
| `table.append()` | FY2007 (単年度) | **約7秒** |
| `table.append()` | FY2008–FY2025 (18年度) | **42秒** |
| `table.overwrite()` | FY2026 area (56,592行) | **6.8秒** (クラッシュした upsert は8分かけて失敗) |

### 選択の根拠

- **FY2007–FY2025 → `append()`**: これらの年度は Silver に未投入で既存行と重複しない。突き合わせ対象が存在しないため、upsert のマッチ処理は純粋な無駄。
- **FY2026 area → `overwrite()`**: 既存行と重複するが、FY2026 は連続した独立区間であり、ステージング結果が当該区間の完全な集合。`delivery_date` 範囲を条件にした区間置換で正しく、かつ安価。

## 6. 恒久対応の提案

### 6.1 Silver 書き込みを区間 overwrite 方式へ変更 (優先度: 高)

`src/pipeline/silver/bronze_to_silver_jepx_spot_price.py` の `upsert_silver_table()` は
テーブル規模の増加に対してスケールしない。`--fiscal-year` 指定時は会計年度の
`delivery_date` 範囲を条件とした `overwrite()` へ置き換えるのが妥当。
日次実行でも同じ経路が使えるよう、置換単位を日次まで細かくできる設計が望ましい。

### 6.2 メタデータ列を upsert の変更検知から除外 (優先度: 中)

`add_metadata()` は実行ごとに `ingestion_time` と `execution_id` を新規採番する。
PyIceberg の `get_rows_to_update()` は非キー列の値変化で更新要否を判定するため、
**業務値が全く変わっていなくても全マッチ行が「変更あり」と判定される**。
FY2026 の base で `updated=5,856` (全既存行) となったのはこのため。
不要な書き込みを避けるには、変更検知の比較対象からメタデータ列を除外する必要がある。

### 6.3 バックフィル用 CLI コマンドの追加 (優先度: 中)

今回は年度ループをシェルスクリプトで組んだが、`docs/architecture/replay_strategy.md` が
定める再構築手順を運用に載せるなら、年度範囲を受け取る一次コマンドとして
`src/main.py` に実装すべき (例: `backfill-jepx --from-fiscal-year 2005 --to-fiscal-year 2026`)。

### 6.4 実行結果判定の厳格化 (優先度: 中)

障害 #1・#2 はいずれも「正常終了」に見えた。オーケストレーター側で
終了コードの明示的な検査と、書き込み後の行数チェックを結果判定に組み込むべき。
`PipelineStepResult` に想定行数と実測行数を持たせ、乖離時に `status="failed"` とするのが最小の改善。

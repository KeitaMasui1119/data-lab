## 2. 前半: a5chin/python-uv 比較の残タスク消化 (#90 〜 #95)

前日の調査レポートが残していた「判断が必要」項目を順に片付けた。

### 2-1. Docker イメージが意図しないステージだった (#90)

`deploy.yml` の `docker/build-push-action` に `target` 指定がなく、Dockerfile の
**最終ステージ**がビルドされていた。ステージ順は `base` → `dev` → `builder` → `prd` →
`dashboard` なので、`ghcr.io/keitamasui1119/voltlake:latest` として公開されていたのは
CLI アプリではなく **Streamlit ダッシュボード**だった。

両方とも publish 対象なので、別パッケージ 2 本に分けた:

| イメージ | ステージ |
|---|---|
| `ghcr.io/keitamasui1119/voltlake/app` | `prd` |
| `ghcr.io/keitamasui1119/voltlake/dashboard` | `dashboard` |

`dashboard` は `FROM prd` なので、matrix に分けず 1 ジョブ内で順にビルドしている。
matrix にすると共通の `base` → `builder` → `prd` を 2 ランナーで二重にビルドすることになり、
それを避けるにはリモートキャッシュの追加が必要になる。

併せて `devcontainer.json` から GCP 鍵パス (完全な死に設定。`google.cloud` を import する
モジュールは 0 件、依存宣言もなし) と git identity のハードコードを除去した。

### 2-2. カバレッジのゲート化 (#91)

CI は `--cov-report=term-missing` を出力するだけで、数値が下がっても PR は通っていた。
実測 73.76% に対し floor を **73** に設定。目標ではなく退行検知が目的で、ラチェット計画を
レポートに残した。

### 2-3. 依存の整理 (#92, #94)

`apache-airflow` は将来利用予定だが import 0 件。`[dependency-groups] airflow` へ移送した。
**`[tool.uv] default-groups = ["dev"]` の追加が本質**で、uv 0.12 系はこれが未設定だと
全グループを既定インストール対象として扱うため、単にグループを分けただけでは
`uv sync` が airflow を入れ続ける。

続けて import 0 件の依存 13 件 (`beautifulsoup4` / `lxml` / `nbformat` / `numpy` /
`pandas` / `pydantic` / `pydantic-settings` / `scikit-learn` / `Scrapy` / `seaborn` /
`cookiecutter` 系 2 / `mkdocs-material`) を削除。推移的依存 44 件と合わせて 57 パッケージ減。

保持したもの:

- `dbt-core` / `dbt-duckdb` / `shandy-sqlfmt` — dbt 着手が近い
- `ipykernel` — import されないが VS Code が venv を Jupyter kernel として認識するのに必要
- `duckdb` — 直接依存として明示済み

### 2-4. ruff ルールの拡大 (#93)

候補ごとに違反数を計測してから採否を決めた。

| ルール | 違反 | 判断 |
|---|---:|---|
| `PTH` | 5 | 採用 |
| `SIM` | 1 | 採用 |
| `RUF` | 56 | 採用 (`RUF001`/`RUF003` は日本語の全角括弧なので ignore) |
| `S` | 51 | **見送り** ← 後に #97 で撤回 |

`RUF100` (未使用 noqa) が 23 件出た。`# noqa: BLE001` が 15 箇所以上あったが、
`BLE001` は voltlake の `select` に含まれておらず、**元々効いていない noqa** だった。

### 2-5. PR 時の Docker build 検証 (#95)

Dockerfile の壊れは `deploy.yml` (main への push) でしか検知されず、main が壊れてからしか
分からなかった。3 つの shippable ステージ (`dev` / `prd` / `dashboard`) を matrix でビルドする
ジョブを追加。push はしない。

hadolint は静的解析なので、シェル文法エラーや apt レイヤの実行時失敗といった
「実際にビルドしないと分からない」問題は検知しない。両者は補完関係。

初回 3-4 分、`type=gha` キャッシュ後は各 30-60 秒。

## 3. 後半: ECC × a5chin の突き合わせ (#96 〜 #98)

軸を変え、**ECC (`~/.claude/rules/ecc/`) が要求する基準**を起点に、それを強制する仕組みが
あるかを見た。

> **ECC はルールを宣言するが強制しない。a5chin は仕組みを持つが固有の判断を要する。**
> 両者は競合ではなく補完関係にあり、噛み合っていないのが実態だった。

### 3-1. `jepx_common` が使われていなかった (#96)

「なぜ `src/pipeline/jepx_common.py` は `common/` でも JEPX パイプライン内でもないのか」
という問いから調査。結論は**現在地が正しい**:

- `common/` は dataset-agnostic 専用 (CLAUDE.md)。4 関数はいずれも JEPX 固有の規約
  (会計年度 4 月始まり、`spot_summary_{FY}.csv`、`raw/jepx/spot_summary/`) を符号化している
- 利用者が `pipeline/raw` / `pipeline/bronze` / `orchestration` / `cli/commands` の
  4 パッケージにまたがる。特定レイヤーに埋めると横方向の依存が 3 本生まれる

ただし**配置ではなく使われ方に問題**があった。会計年度の判定式が 4 箇所、ファイル名の
書式が 3 箇所に直書きされており、しかもそのうち 3 ファイルは `jepx_common` を既に
import していた。

```python
def resolve_default_raw_object(target_at: datetime) -> tuple[str, str]:
    fiscal_year = target_at.year if target_at.month >= 4 else target_at.year - 1  # = resolve_fiscal_year()
    file_name = f"spot_summary_{fiscal_year}.csv"                                 # = resolve_spot_summary_file_name()
    object_key = resolve_spot_summary_object_key(target_at)                       # ← ここだけ正しい
    return object_key, file_name
```

6 箇所すべてをヘルパー経由に寄せ、会計年度の境界 (2026-03-31 → FY2025、
2026-04-01 → FY2026) で出力が完全一致することを確認した。

### 3-2. `S` (bandit) の採用 — #93 の判断を撤回 (#97)

**このセッションで最も重要な修正。**

ECC `python/security.md` は `bandit -r src/` を明示的に要求している。ruff の `S` は
その bandit の移植である。#93 で「S608 が 45 件出るから」を理由にセット全体を捨てたが、
その結果 **本来検出したい `S602` (`shell=True`) まで無効なまま**になっていた。
ノイズの多いルール 1 つを避けるためにセット全体を捨てるのは、トレードとして逆。

正しい形は、誤検知するルール 1 つだけを理由付きで無効化すること:

```toml
select = [..., "S"]
ignore = [
    ...,
    # S608 は silver/gold の DuckDB クエリ 45 箇所を一律に指摘する。いずれも
    # Iceberg のテーブル名や列名を f-string で埋める形で、値は schema CSV と
    # 会計年度などのバインド済みリテラルのみ。外部入力が SQL に到達する経路がない。
    "S608",
]
```

実質的な指摘 6 件のうち、**`S101` には実害があった**:

```python
TIMESLOT_COLUMNS: tuple[str, ...] = _generate_timeslot_columns()
assert len(TIMESLOT_COLUMNS) == 48   # ← python -O で消える
```

48 スロットという不変条件を守る唯一のチェックが `assert` で、`python -O` では文ごと
除去される。本番を最適化フラグ付きで動かした瞬間に静かに無検査になっていた。
明示的な `raise` に置換し、マジックナンバーを `TIMESLOT_COUNT` に括り出した。

**ゲートが効くことを実証した。** 設定を書いただけで満足しないよう、意図的な違反を
`src/` に仕込んで捕捉を確認 (確認後削除):

```
S101 Use of `assert` detected
S602 `subprocess` call with `shell=True` identified, security issue   ← 本質
S108 Probable insecure usage of temporary file or directory: "/tmp/x"
```

### 3-3. 残る 4 ギャップの解消 (#98)

| ECC のルール | 対応 |
|---|---|

| `testing.md` | `--cov-branch` + `.coveragerc` |
| `python/testing.md` unit/integration | `unit` マーカー登録 |
| `development-workflow.md` ローカル = CI | `noxfile.py` 新設、CI 4 ジョブを nox 経由に |

`C901` の唯一の違反 `setup/manage_iceberg.py:main` (11 > 10) を分割する過程で
**実際の欠陥**が出た。`table create` で `--csv` を省略すると `logger.error` して `return`

```
$ python -m setup.manage_iceberg table create --name x   # --csv なし
修正前: exit=0     修正後: exit=2
```

分割の副産物としてテストが書けるようになり、**0% → 83%**。

CI の 4 ジョブはすべて `uv run nox -s <session>` に付け替えている。乖離が起きると
**短く打ったローカル版のほうが通ってしまう**のが厄介だったので、これが本質的な効果。

## 6. 現在の品質ゲート構成

```
pre-commit (ローカル、コミット毎)
  ├─ whitespace / JSON / TOML / YAML / XML パース
  ├─ detect-private-key
  ├─ ruff check + ruff format      ← S (bandit) / C901 / PTH / SIM / RUF 含む
  ├─ actionlint / hadolint
  └─ pyright

GitHub Actions (push / PR to main) — 7 ジョブ定義 / 9 チェック
  ├─ lint / format / typecheck / test   → すべて uv run nox -s <session>
  ├─ actionlint / hadolint
  └─ docker-build (dev / prd / dashboard の matrix = 3 チェック)

deploy.yml (main への push、CI 成功後)
  └─ app / dashboard を GHCR へ publish

Renovate (週次)
  └─ blast radius で automerge を分離
```

`uv run nox` でローカルから CI と同一のチェックが回る。

## 2. JEPX_SPOT_PRICE パイプラインの構造理解 (Q&A)

実装変更を伴わない調査・説明のやり取り。要点を記録する。

### 2-1. 全体構成

```
JEPX サイト (POST) → Raw (RustFS gzip) → Bronze (Iceberg append) → Silver (3テーブル) → Gold (3テーブル)
```

- **Raw** (`pipeline/raw/source_to_raw_jepx_spot_price.py`): 年度ぶん CSV を毎回まるごと POST 取得し、SHA256 が前回と同じならスキップ
- **Bronze** (`pipeline/bronze/source_to_bronze_jepx_spot_price.py`): cp932 デコード → 文字列のまま append
- **Silver** (`pipeline/silver/bronze_to_silver_jepx_spot_price.py`): DuckDB で型変換・重複排除・バリデーションし、PyIceberg `overwrite()` で会計年度ウィンドウを洗い替え。`base`/`block`/`area` の3テーブルに分岐
- **Gold** (`pipeline/gold/silver_to_gold_jepx_spot_price.py`): area×base を JOIN し `daily`/`period_profile`/`area_spread` の3テーブルを生成

### 2-2. Raw の重複排除はリクエストそのものは省略しない

`sha256 = hashlib.sha256(scraped.body).hexdigest()` は**保存をスキップするだけ**で、HTTP リクエストは毎回発生する。防いでいるのは通信ではなく raw への重複保存と ingestion_log への無駄なエントリ。

manifest (`raw/jepx/spot_price/manifests/year={fy}/latest.json`) は**会計年度ごとに別オブジェクト**なので、他年度を取得してもその年度の重複判定には影響しない (`2026→2023→2026` と取得しても2回目の2026は正しく `skipped` になる)。

### 2-3. Silver の書き込みは PyIceberg の `overwrite()`

DuckDB は変換 (`iceberg_scan()` で bronze を読み、SQL で加工) のみを担当し、実際の書き込みは `common/silver_write.py` の `table.overwrite(data, overwrite_filter=...)` という **PyIceberg ネイティブ API**。

`overwrite()` は「キーで突き合わせて更新する UPDATE/MERGE」ではなく、**「フィルタに一致する範囲を削除 → 新データを挿入」を1トランザクションにまとめたもの**。区別:

| メソッド | 動作 | 使用箇所 |
|---|---|---|
| `table.append(df)` | 純粋な INSERT | Bronze 層 |
| `table.overwrite(df, overwrite_filter=...)` | 範囲 DELETE + INSERT (アトミック) | **Silver/Gold 層** |
| `table.upsert(df, join_cols=...)` | キー突き合わせで更新/挿入 (未使用) | — |

`silver.jepx_spot_price_base` の場合、`overwrite_filter` は `delivery_date` の範囲のみで構築されており (`build_delivery_window()`)、`time_code` は削除条件に入らない。したがって:

- ステージング側の重複排除は `(delivery_date, time_code)` ごとに `ingestion_time` 最新の1行を採用 (正しい)
- しかし削除は **`delivery_date` の範囲を丸ごと** (該当会計年度、または今回ステージされた有効行の最小〜最大日付) 行い、`time_code` 単位のピンポイント削除ではない

この設計により、「silver に既に有効な値があるキーの、bronze 側最新行だけがバリデーション落ちした」場合、upsert なら手を付けずに残るはずの値が、overwrite では**ウィンドウごと消えて再挿入されない**という挙動が生まれる (bronze に一度もデータが無いケースとは別問題)。これはコード側のコメントに明記された意図的なトレードオフ。

### 2-4. なぜ upsert ではなく overwrite なのか — 実測の再確認

2026-08-08 の FY2005–2026 本番バックフィルで実際に起きた障害を再確認した。誤解を訂正した点:

- **「ローカル環境だから OOM した」ではない。** コンテナは 15GB 搭載・実行時空き約9GB で、レポート (`docs/reports/reports_20260808_10c4679e-4370-49d3-9b8c-92f890c5eade.md`) には「OS レベルのメモリ不足ではなくプロセス内での破綻」と明記されている
- `Transaction.upsert()` が `(delivery_date, time_code, area_name)` の 56,592 キーを OR 連結した巨大な述語を構築し、3,361,008 行の `silver.jepx_spot_price_area` をスキャン → SIGSEGV (終了コード139) で 8分22秒後にクラッシュ
- 単年度実行でも FY2005 で 3分21秒、FY2006 で 4分31秒とテーブル肥大に伴い増加傾向で、環境依存の偶発事故ではなく **upsert のコストがターゲットテーブル行数×ソースキー数に比例して伸びる構造的な問題**
- 同じ FY2026 area を `overwrite()` に切り替えると 6.8秒で完了

つまり本番相当のメモリを積んでも、テーブルが年々増える以上いずれ同じ壁にぶつかる。`overwrite()` への切り替えは一時しのぎではなく恒久対応、という位置づけ。

### 2-5. 副次的に確認した既知の drift

オーケストレーターの `--run-gold-step` は今も `dbt run --select tag:gold` を叩く設計 (`src/dbt/jepx_power/` にモデルは無い) だが、実際の Gold 実装は `ingest-jepx-silver-to-gold` (Python/DuckDB) という別コマンド経由。セッション中はこれを未文書の drift と見て指摘したが、**実際は `docs/architecture/pl_jepx_spot_price_design.md` セクション3 "Note: the orchestrator's gold step is not the gold layer" に既に明記済み**だったことを確認した。新規の発見ではなく、既存ドキュメントの再確認。

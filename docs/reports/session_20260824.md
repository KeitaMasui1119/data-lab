## 3. PR #108: `metadata.pipeline_run_log` の新設

### 発端

「ETL がどの実行で何のファイルを取ったか記録するテーブルが要るのでは」という質問。調査の結果：

- **既にあった**: `metadata/raw_ingestion_log.parquet`（ファイル単位の記録）
- **無かった**: 実行単位の記録。オーケストレーターは `PipelineStepResult` のリストを組み立てるが、ログに出力するだけで捨てていた

### 設計判断

- **1テーブル・ステップ粒度**（`run_id` + `step_seq` で識別、run 単位は GROUP BY で導出）。2テーブル構成（run + step）も検討したが、オーケストレーターが既にステップリストを返す構造なのでそれに合わせた
- `status` 列は監査カラム注入と衝突するため `step_status` に命名
- `PipelineStepResult` に `started_at`/`ended_at` を追加し、`stamp_step_timing()` で呼び出し側がスタンプ。未計測ステップは 0 ではなく null（0 だと「一瞬で終わった」と誤読される）
- `record_pipeline_run()` は例外を raise せず log するのみ（監査書き込みの失敗で、既に完了した ETL 実行を失敗扱いにしない）
- `month(logged_date)` パーティション（1日数行しか増えないため）

### 実データでの検証

`provision-metadata-tables` でテーブル作成 → 4ステップ append → 読み戻し → 検証行削除、まで実施。**この過程で `add_metadata()` が監査カラム5つのうち `source_data`/`status` を付与しないバグを発見**（ユニットテストでは検出不可、実カタログに当てて判明）。修正し `build_run_log_write_frame()` にリグレッションテストを追加。

## 4. PR #109: `execution_id` を Raw/Bronze へ配線 + ingestion log 共通化

### 前提作業として重複を統合

6スクレイパーが `_build_empty_ingestion_log()`/`_update_ingestion_log()` を個別に保持しており、`execution_id` を足すなら6箇所同じ変更が必要になるため、先に `common/raw_ingestion_log.py` へ集約（**-430行**）。

### 集約中に発見した既存バグ

JEPX 版だけ `is_latest` の付け替えを `fiscal_year` のみでスコープしており、**JEPX のスナップショット保存が同一年度の他データセットの行まで `is_latest=False` にしていた**。共通版は必ず `dataset` でも絞る。年度キー方式（JEPX/supply_demand）と日付キー方式（OCCTO/power_usage）は「fiscal_year が指定されていれば優先」の1ルールに統合。

### execution_id の配線

`orchestrator が run_id を発行 → raw（ingestion log）→ bronze（行に刻む）→ silver（PR #108 で対応済み）→ run log` という経路を完成。CLI 単体実行は何も渡さず自分で ID を生成（それ自体が1ステップの実行として正しい）。

### 副次的に発見・修正したバグ

Hokuriku は1スナップショットから3テーブル（daily_summary/hourly/interval5）に書き込むが、`add_metadata()` に毎回 `None` を渡していたため**同一取り込みに3つの異なる `execution_id`** が付与されていた。1回だけ解決して共有する形に修正。

### 検証

実データ2,114行の ingestion log の**コピー**に対して append を実行し、行数維持・既存行 null 維持・FY2026 JEPX 行の supersede・**他データセット2,090行が無傷であること**を確認。

## 6. PR #111: `common/` utility 整理（2.11節クローズ）

### ファイル統合

| Before | After |
|---|---|
| `utilities.py` + `logging_utils.py` | `utils.py` |
| `pipeline_utilities.py` | `polars_utils.py` |

`utils.py` が再び何でも入れ物にならないよう、モジュール docstring と CLAUDE.md 両方に「ドメインを持たないものだけ」という基準を明記。

### 2.11節の実態

`resolve_default_target_date` の**関数本体は既に集約済み**で、5モジュールには移動先を指す注記コメントのみが残存（ドキュメント未更新だっただけ）。ただし**テスト側の重複**（5ファイルに同名テスト、うち3つバイト一致）が残っており、`tests/common/test_utils.py` へ統合。

結果：510テスト全通過、カバレッジ 73.24%→73.37%（テストは減ったのに向上）。

## 7. PR #112: 2.9節を実測して Won't Fix クローズ

### 調査結果

- **105行 import ブロック自体は解消済み**（`src/cli/` 分割で `main.py` は39行・import 5行に）
- **起動コストは `cli/commands/` へ移動しただけ**

実測（`-X importtime`）：

```
--help 全体                    2,350 ms
  cli.commands（累積）          2,091 ms
    boto3 709ms / pyiceberg 704ms / polars 357ms
素の uv+python+argparse          198 ms
```

AST 解析で、`configure()`（パーサ構築）が必要とするのは重いモジュールに置かれた軽い定数（パス文字列・`3.0`）のみで、ハンドラ専用 import 40個は全て関数内へ遅延可能と特定。理論上10倍（約250ms）まで削減可能だが、**実パイプラインは数分走るため2秒は誤差**、対して変更は7モジュール全体に及ぶとして Won't Fix 判断。実測値・原因・対応方針・再検討トリガー（CLI 高頻度呼び出し用途が出た場合）をドキュメントに記録。

## 8. PR #113: データセット命名の統一（既存パイプライン整理の着手）

### 背景

ユーザーから「新機能より、既存6データセット間の一貫性整理を優先したい」との方針転換があり、6データセット（JEPX/OCCTO/power_usage/supply_demand×3）の Raw/Bronze/Silver/オーケストレーター/CLI 構造を横断比較した。

### 比較して見つかった5つの不統一

| | 内容 | このPRでの対応 |
|---|---|---|
| A | `bronze_status` が6つ中2つ（JEPX/OCCTO）でしか機能していない | 未対応（次PR候補） |
| B | Raw→Bronze の引き当てが2系統（ingestion log 経由 / object key 直指定） | 未対応（次PR候補） |
| **C** | **`dataset` 名の表記が不統一**（`jepx.spot_price` だけドット区切り、`occto_unit_generation` だけモジュール名と不一致） | **✅ このPRで対応** |
| **D** | **JEPX の Raw だけ `DATASET_NAME`/`OBJECT_PREFIX` 定数を持たずリテラル直書き** | **✅ このPRで対応** |
| E | オーケストレーターが2/6データセットにしか無い（A の直接原因） | 未対応（次PR候補） |

ユーザーが C+D（命名統一）を選択。

### 対応内容

- `jepx.spot_price` → `jepx_spot_price`、`occto_unit_generation` → `occto_unit_generation_actuals`
- JEPX Raw に `DATASET_NAME`/`OBJECT_PREFIX` を新設し、スナップショット/マニフェストキー組み立てもこの定数経由に
- OCCTO・power_usage Bronze が独自定義していた `DATASET_NAME` を削除し、Raw モジュールから import する形に統一（1データセット1定義）
- オブジェクトプレフィックス（物理パス）は変更なし（既存スナップショットが迷子になるため）

### 本番データのマイグレーション

2,114行の実 ingestion log を書き換え。手順：スクラッチコピーで検証（行数維持・`dataset` 以外の列が不変・両データセットが新名称で resolve 可能）→ 本番適用 → 再読込確認 → コピー削除。

```
--- before (2114 rows) ---        --- after (2114 rows) ---
  jepx.spot_price          23       jepx_spot_price                23
  occto_unit_generation     4       occto_unit_generation_actuals   4
  power_usage_hokuriku   2084       power_usage_hokuriku         2084
  supply_demand_*(×3)       3       supply_demand_*(×3)             3
```
